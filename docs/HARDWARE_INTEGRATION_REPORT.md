# PRW-Wild — Physical Hardware Interface & Control Integration Report

## 1. System Architecture & Operating Principles

The PRW-Wild hardware integration bridges the virtual 3D wildlife digital twin with physical deterrent and surveillance electronics. 

The essential operating principle is:
> **The virtual animal movement is the master controller.**
> Real-world events are generated by virtual animal motion, activating corresponding physical outputs without requiring actual noisy physical sensor measurements to drive the prototype.

---

## 2. Truth in Hardware Reporting & Three-State Model

A core directive of this implementation is **Truth in Telemetry**:
- **Simulated State:** The virtual detection state calculated from agent spatial coordinates in the digital twin.
- **Commanded State:** The state dispatched by the controller (either via automated FSM or manual operator toggle).
- **Hardware-Confirmed State:** The state acknowledged back from the physical peripheral over serial UART or TCP socket.

If a physical peripheral is not physically plugged into the host, the system truthfully reports:
- `connected: false`
- `status: "HARDWARE_ABSENT"`
- `diagnostics: "Port / IP unreachable — running in SIL virtualization fallback"`

**The system never generates fake connection confirmations or fabricated hardware acknowledgements.**

## 3. Tri-Mode Operating Architecture

The service (`src/prw_wild/hardware/control_service.py`) implements three explicit operating modes:

```
  ┌─────────────────────────────────────────────────────────────┐
  │                 OPERATING MODE SELECTOR                     │
  └───────┬─────────────────────┬─────────────────────┬─────────┘
          │                     │                     │
          ▼                     ▼                     ▼
┌──────────────────┐  ┌──────────────────┐  ┌──────────────────┐
│ SIMULATION_ONLY  │  │  HARDWARE_TEST   │  │  AUTO_HARDWARE   │
│                  │  │                  │  │     CONTROL      │
│ • Safe SIL mode  │  │ • Manual toggles │  │ • Sim is master  │
│ • Outputs disarm │  │ • Bench benching │  │ • Virtual animal │
│ • No side-effects│  │ • L1, L2, L3 test│  │   drives outputs │
└──────────────────┘  └──────────────────┘  └──────────────────┘
```

1. **`SIMULATION_ONLY`:** Safe Software-in-the-Loop virtualization. Physical hardware drivers remain completely disarmed. Virtual animals and 3D visualization run unrestricted.
2. **`HARDWARE_TEST`:** Engineering bench-test mode. Operators manually toggle Layer 1, Layer 2, and Layer 3 outputs, test relays, and trigger emergency all-off sequences.
3. **`AUTO_HARDWARE_CONTROL`:** Master autonomous coupling. Virtual animal spatial intrusions into Layers 1, 2, and 3 dispatch automated activation commands to physical drivers.

## 4. Hardware Adapters & Peripheral Specifications

### Deadlock-Free Thread Safety
To ensure absolute reliability during high-frequency telemetry polling and concurrent UI requests, `HardwareManager` uses recursive re-entrant locks (`threading.RLock()`) across all public methods, completely preventing deadlocks during nested connection status queries.

## 5. API Endpoints & Verification Suite

The hardware service exposes four high-performance REST endpoints in `src/prw_wild/web/server.py`:
- `GET /api/hardware/status`: Returns current mode, layer states, manual overrides, and command telemetry log.
- `POST /api/hardware/mode`: Switches operating mode (`SIMULATION_ONLY`, `HARDWARE_TEST`, `AUTO_HARDWARE_CONTROL`).
- `POST /api/hardware/command`: Dispatches layer actuation commands (`ON`, `OFF`, `STROBE`, `PTZ_LOCK`).
- `POST /api/hardware/emergency_stop`: Immediately de-energizes all physical and simulated outputs within $< 10\text{ms}$.
